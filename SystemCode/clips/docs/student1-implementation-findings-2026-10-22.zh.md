# 用户需求理解与情境推理模块总结

## System Development & Implementation

本项目构建了旅行需求理解与情境推理模块，将用户的自然语言描述转换为结构化、可逐轮修改且可追溯的穿搭需求，为后续时尚参考检索、商品检索和搭配推荐提供统一输入。模块结合本地语言模型、确定性规则、活动与地点知识图谱，分别处理用户表达、天气条件及活动场所要求。

### 需求理解与对话管理

系统采用预训练 Qwen3-0.6B 提取目的地、旅行日期、预算、币种、活动和风格等信息，并使用 Pydantic、业务规则及原文证据检查验证模型输出。用户事实与推理结果分开保存，避免模型自行补充天气、预算或偏好。对缺失、歧义或不合法的信息，系统保留已收集内容，并针对需要澄清的字段继续追问。

对话状态区分待确认信息与已确认需求。用户可以逐轮补充目的地、日期和预算，也可以通过局部修改更新已有需求。修改采用 set、add、remove 操作，保留未提及字段；无效更新不会覆盖原状态。价格偏好与预算上限分别表达，因此“便宜一点”不会直接转换为一个未经用户指定的新预算。

日期处理支持标准日期、斜杠日期、英文月份缩写、中文日期及部分相对日期，并能在用户只补充年份时恢复日期范围。对可能存在日月顺序歧义的输入，系统要求进一步确认。活动和风格作为可选信息，用户可以从知识图谱支持的候选中选择，也可以跳过；候选建议在明确选择前不会成为用户需求。相关交互已接入团队现有网页界面，支持多选气泡、选择反馈和行程确认。

### 天气与知识图谱推理

天气模块通过 Open-Meteo 获取地理位置与旅行日期对应的预报，并利用确定性规则生成保暖、分层及防雨等衣物类别与功能需求。对于超出或跨越预报窗口的行程，系统使用明确标识的历史气候参考，避免将历史统计与旅行预报混为一谈。

历史气候数据来自2015至2024年的 ERA5 日数据，覆盖12个国家的15座城市，形成180条月度统计。数据通过 JSON 快照共享，并由本地 SQLite 提供查询；保留位置、时间范围、统计方法和来源信息。国家级输入需进一步明确城市，未知城市提供显式补库入口。天气接口失败、位置不明确或数据不可用时，系统保留未知状态，不以默认晴天或邻近城市代替。

Activity KG 包含16类活动、22个 Style 节点，共90个节点、203条关系及13个来源。图谱通过受限的一跳与多跳路径连接活动、场合、正式程度、风格和属性，并保留条件与证据。审美方向与功能需求分开表达，避免将多种候选风格同时变成强制约束。晚餐等活动在需要时进一步询问 dress code，而不直接假定正式程度。

地点 KG 覆盖8个国家的100个 Place，支持具体地点、活动、是否入内及场所着装规定等条件。其753条基础记录导出为601个节点及1214条边，其中包括别名、来源及溯源结构。活动与地点推理结果结合天气需求、用户偏好和限制，形成结构化输出及 ExpandedFashionContext，交给下游模块使用。

系统支持本地 Python 推理和 Neo4j 后端。Activity KG 可存储于 Neo4j，并通过真实 Cypher 查询验证保留的有界推理路径；条件推理由 Python 执行。地点 KG 使用本地推理。

### 知识审核与可追溯性

知识维护区分来源支持的陈述与项目启发式，保留适用条件、来源读取等级和审核状态。项目负责人已完成现有知识审核，活动节点、关系、来源以及地点 KG 的753条记录均已记录为通过。

审核记录包含审核人、时间、记录级快照、内容及规范指纹。审核应用前进行结构和引用校验，并保留备份及恢复机制；共享运行快照与导出文件同步更新。审核工具对依赖链进行检查，防止仅批准来源或地点后，相关规则被自动视为已审核。记录内容改变后，原审核结果可以失效，修改后的内容需要重新审核。

## Findings and Discussion

### 测试集构建与评估设计

项目采用分层评估，分别检查语言理解、对话状态、知识推理、天气处理与接口集成。模型评估保留原始输出及规则处理后的结果，以区分模型能力与系统校验带来的改善。功能测试则针对明确的输入、预期输出及状态变化进行验证。

| 测试集或验证层次 | 构建方式与规模 | 主要覆盖内容 |
|---|---|---|
| 多语言需求理解集 | 32个场景、40轮输入，包括25轮英文、13轮中文及2轮混合语言 | 完整与缺失需求、币种歧义、跨年日期、否定表达、场合限定、排除项、不合法输入及多轮修改 |
| 英文开发子集 | 从多语言集中选取25轮英文输入 | 聚焦英文工作流程，检查字段抽取、局部修改、解释与确认意图；用于开发回归 |
| 补充英文诊断集 | 另外编写16轮输入 | 新地点与风格、金额精度、缺失币种、日期修改、删除排除项、歧义确认及无明确金额的低价偏好 |
| 对话控制器场景集 | 6个场景、19轮交互 | 混合日期格式、只补年份、日期歧义保护、逐轮收集信息、明确选择活动及跳过风格 |
| 地点推理场景集 | 16个固定预期场景 | 季节差异、室内外区分、入内条件、场所着装规定、活动选择及信息缺失 |
| 自动化与真实组件验证 | 单元与集成测试，配合天气和 Neo4j 真实查询 | 规则边界、状态保留、审核过滤、证据路径、数据一致性、异常处理及接口行为 |

多语言集包含3段连续对话，英文开发子集包含其中2段。逐轮评估提供预设的上一轮状态，以定位单次抽取错误；连续对话评估则传递实际生成状态，观察错误是否累积及最终需求是否正确。英文开发子集与多语言集存在重叠，不作为额外独立样本累计。

评分同时考虑字段内容、缺失字段、修改意图、不应出现的新增信息、校验结果和最终状态。完整正确要求各项均符合预期，避免大量未改变字段掩盖少量关键错误。对不合法输入，另行检查系统是否安全拒绝；拒绝正确与抽取完整正确分别计分。测试保留模型版本、提示词与数据集指纹，便于复核结果。

### 开发过程与指标变化

初始检查发现，小模型虽然能够生成可解析的结构化结果，但仍会遗漏用户事实、补充未表达偏好、混淆否定与肯定，以及在需求修改时返回整份请求。针对这些问题，项目逐步完善提示词、原文证据核对、词表归一化、局部更新和确认机制，并通过日期处理与对话控制器改善信息收集流程。

| 数据集 | 初始阶段原始模型 | 初始阶段规则增强 | 改进后原始模型 | 改进后规则增强 |
|---|---:|---:|---:|---:|
| 多语言需求理解集 | 3/40 | 14/40 | 4/40 | **23/40** |
| 英文开发子集 | 4/25 | 21/25 | 4/25 | **22/25** |
| 补充英文诊断集 | 1/16 | 15/16 | 1/16 | **16/16** |

多语言集的规则增强完整正确率由35.0%提高至57.5%，增加22.5个百分点。英文开发子集达到88.0%，补充英文诊断集达到100%。这些变化表明，原文核对和确定性状态处理改善了已覆盖场景中的系统表现；原始模型完整正确数仍较低，进步主要来自系统工程，而非模型训练或微调。

连续对话达到预期最终状态的比例由0/3提高至2/3，两段英文对话成功，中文对话仍未成功。英文开发子集的后续意图分类为8/8，预期修改字段正确数为8/8；补充英文诊断集分别为7/7和5/5。两批英文评估均未记录额外修改用户未要求改变的字段，支持局部更新机制在这些场景中的有效性。

对话控制器场景集的6个场景、19轮检查均符合预设预期，说明灵活日期解析、补充信息、可选活动选择和明确确认可以协同工作。该评估使用真实模型抽取及确定性参考回复，衡量需求和状态正确性，不衡量生成文案的自然度。

### 功能与审核验证结果

| 验证项目 | 结果 | 结果含义 |
|---|---|---|
| 共享仓库自动化回归 | **613项通过，63项跳过** | 覆盖代码功能和接口行为；跳过项未计作通过 |
| Activity KG 源项目测试 | **14/14通过** | 验证场景、路径、条件、审核过滤及导出 |
| 地点 KG 源项目测试 | **60/60通过** | 包括审核保存、依赖链、批准失效、修改再审、冲突检测、回滚及恢复 |
| 地点推理场景 | **16/16通过** | 关闭草稿模式，通过真实命令行检查应有需求、禁止误触发项和缺失信息 |
| Neo4j 与本地推理对照 | **4/4一致** | 覆盖徒步、博物馆及不同条件和深度的晚餐查询，证据路径均通过真实 Cypher 验证 |
| 严格审核链验证 | **3个场景的12项需求均链完整** | 检查来源、地点、规则、需求及单品映射等依赖，而非仅检查单条 approved 标记 |
| 天气数据处理 | **2/2通过** | 验证真实城市预报和远期历史参考查询，以及两类数据的语义区分 |

测试过程也暴露了部分用例依赖“所有知识均待审核”的数据假设。项目将待审核状态改为显式测试样本，继续检查未审核和拒绝知识的过滤，同时增加已审核知识可用性、审核前后事实一致性和共享快照指纹检查，避免知识审核完成后失去对审核保护逻辑的覆盖。

### 主要发现与局限

**结构正确不等于语义正确。** 原始模型的完整正确数远低于规则增强结果，说明解析成功不能替代事实核对。多语言集的原始纯 JSON 输出由初始阶段的30/40变为8/40，允许代码围栏的解析器仍可解析40/40。提示词从通用需求抽取转向英文流程后，各项指标并未同步改善，不能将整个系统描述为全面提升。

**英文流程的改善尚未推广到中文。** 多语言集的13轮中文输入在严格完整评分下均未通过，其中包括一个被正确拒绝的不合法输入。主要问题涉及“新币”遗漏、活动归一化、无依据的排除项、修改意图及多轮状态更新。项目目前更适合以英文为主要支持语言。

**安全拒绝与抽取成功需要分别报告。** 英文开发子集仍有3例严格失败，分别为不存在的日期、负预算和不支持的小数金额精度。系统正确拒绝了这些输入，但未保留满足严格抽取评分的完整候选。因此，校验结果正确为25/25，完整正确为22/25，不将安全拒绝改计为抽取成功。

**知识可追溯不等于获得专业共识。** 现有知识已由项目负责人审核，但尚未形成双人独立审核或专业专家一致度结果。地点KG的62个来源中，7个仍标为搜索摘录、30个为相关章节阅读、24个为页面正文阅读、1个为项目本地规则。审核状态不会提高来源读取等级，也不会把项目启发式转为普遍适用的事实。活动、文化和场所条件仍需保留。

**评估主要支持开发场景内的正确性。** 测试样例及合成标签已用于开发和错误分析，缺少经过独立人工复核的保留测试集，不能将小样本100%解释为生产准确率。数据集部分重叠，也未开展控制其他因素不变的消融实验，因此不能单独量化提示词、规则或图谱各自带来的收益。字段F1、人工推理质量评分和独立评审一致度仍需补充。

**组件可运行不代表完整推荐质量已得到证明。** 自动化回归中63项跳过主要与缺少依赖、未启用的真实集成或付费预览有关。天气阈值仍为项目规则，十年历史统计不等于标准30年气候常态或旅行日预测；城市级天气也不能直接代表山地和室内环境。当前评估不用于证明最终搭配质量或用户满意度。

## 与 proposal 的差异供报告整合使用

本节为整合说明，可根据总报告结构删去或并入相应章节。

| 项目 | 与 proposal 的对应或差异 |
|---|---|
| Qwen3-0.6B | 与 Stage 1 设计一致；LoRA 原为可选实验，未实施不应写成缺少必做模块。 |
| 需求理解方式 | **实施细化**：实际采用模型、原文证据规则、schema 校验及用户确认的组合，不能仅以原始模型描述整个模块。 |
| 活动必填条件 | **相对 §7.2 早期 demo 调整**：活动允许为空；目的地、起止日期、预算与币种齐全后，可继续处理。 |
| 日期与交互 | **扩展**：增加灵活日期解析、只补年份、活动与风格候选、多选及跳过。 |
| 历史天气 | **原计划落地并扩展**：增加月度统计数据库、覆盖管理、来源记录和显式补库流程。 |
| 地点 KG | **扩展**：在五类节点的 Activity KG 外增加地点、场所要求与条件模型。 |
| Neo4j | **实施方式说明**：支持本地推理与 Neo4j；Python 执行条件推理，Neo4j 提供存储及路径验证。 |
| 人工审核 | 负责人已完成现有知识审核，并保留逐条记录；尚无双人独立审核或专家一致度指标。 |
| 评估指标 | 已有完整正确性、格式有效性、意图与修改字段、连续状态、路径一致性及场景断言；字段F1、人工质量评分和独立泛化评估尚不完整。 |
| 天气范围 | 湿度等部分属性、阈值的独立验证及特殊地理环境处理仍有限。 |

## 待进一步审查的事项

- 合成评估标签，尤其是歧义、否定、不合法输入和确认状态的预期。
- 原文读取等级仍为搜索摘录的7个来源，是否需要补充正文证据或缩小知识表述。
- 天气阈值及个人敏感性、山地和室内环境的适用范围。
- 独立英文与中文测试集、人工评审一致度及字段F1。
